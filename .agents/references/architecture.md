# Architecture

## Rules for this file

1. Agents do not edit this file. Only the user edits it, or an agent the user explicitly allowed for that one change.
2. This file describes the allowed target: code that does not match is fixed in the same change, never written down here.
3. Files and folders that match a pattern listed here are allowed. A new pattern, file kind, package or concept needs the user's approval first, and its line lands in the same change.
4. A tree line is a name pattern plus what it holds, in about 15 words.
5. No history, dates, owners or workflows. Skills own workflows and point to this file.

## 1. How Agents Mail works

One Cloudflare Worker serves REST and MCP behind a bearer token, receives mail through Email Routing, sends it through the `send_email` binding, and purges old mail on a cron.

### Layers

Each layer is a `make*` factory that takes its binding or `env`; tests inject fakes through `makeWorker(deps)` or the env.

| Layer | File | Owns |
|---|---|---|
| `makeDatabase` | `database.ts` | D1 reads and writes |
| `makeStorage` | `storage.ts` | R2 attachment files |
| `makeOutbox` | `outbox.ts` | the `send_email` binding and its errors |
| `makeClassifier` | `classifier.ts` | TypeSafe JEV categories and injection scores |
| `makeMail` | `mail.ts` | every mailbox operation, built on the layers above |
| `makeMcp`, `makeWorker` | `worker.ts` | MCP tools, the Hono app and the `fetch`, `email` and `scheduled` handlers |

### Naming

- Methods are single words, Laravel style: `list`, `get`, `send`, `destroy`.
- Exports from `worker.types.ts`, `worker.constants.ts` and `worker.utils.ts` start with `worker`: `WorkerSendParams`, `WORKER_MAX_HEADER`, `workerClip`.
- Types take the method's name: `send()` takes `WorkerSendParams` and returns `WorkerSendResult`, validated by the `workerSendParams` schema.

## 3. Standards

- **Fewer files.** A function with one caller is inlined at that caller, and so is one with two callers and at most 3 lines. The `make*` layers stay: they are the seams tests inject fakes through.
- **No comments.** The code explains itself.
- **Validation.** Parse request bodies, queries, MCP input and JEV answers with the schemas in `worker.types.ts` at their boundary; code inside stays typed and throws `workerProblem()`.
- **Inbound mail.** It is attacker-controlled: every stored field is sized in bytes with `workerClip()`, and limits live in `worker.constants.ts`.
- **Tests.** Test the main flows through the Worker's handlers (`fetch`, `email`, `scheduled`, MCP): the happy path plus each error path, one test per behaviour. Skip what types or zod already guarantee. Merge assertions that share setup. Fakes come from `tests/fakes.ts`; the suite has no `vi`.

## 4. Playbook

- **Setting:** a var in `wrangler.jsonc` or a secret in `scripts/worker-deploy.ts`, documented in the README and the skill.
- **Route or MCP tool:** schema in `worker.types.ts`, operation in `makeMail`, route or tool in `worker.ts`, tests through `tests/client.ts`.
- **Schema change:** a new file in `migrations/`, and the queries that read it in `database.ts` and `worker.constants.ts`.
